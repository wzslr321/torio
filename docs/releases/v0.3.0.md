# Torio v0.3.0

## Highlights

### Linux on x86_64 is a supported host

Torio ran on one host. It now runs on two: `darwin/arm64` and `linux/amd64`.

That is a matrix rather than a list of platforms that happen to work. Each row
carries the hypervisor driver, the guest architecture, and the guest image's URL
and digest — on macOS, Lima's `vz` driver on `aarch64`; on Linux, `qemu` on
`x86_64` over KVM. Both rows pin the same Ubuntu 24.04 build, so a guest differs
from its counterpart in machine code and in nothing else.

Two hosts are absent on purpose. Intel Macs cannot run `vz`, and a darwin/amd64
host would have to emulate the guest. arm64 Linux is plausible and unproven:
adding it costs one row and a digest the table already names, but a row nothing
has ever booted is a claim, and this table is read as a guarantee. ADR-0002
records both, and the error an unsupported host gets names the matrix rather
than restating it in prose that can fall behind.

What had pinned Torio to macOS was never the host code. There was no
`runtime.GOOS` branch outside version reporting, paths came from XDG rather than
`~/Library`, and the trust layer was already built `darwin || linux`. It was four
string literals describing the managed VM, and the packaging around them.

### One table, both sides of the question

Those four values — driver, architecture, image URL, image digest — lived in two
places that had to agree. The template renderer wrote them into the YAML handed
to `limactl create`; the verifier compared Lima's report against them. That is
the right shape while exactly one host is supported, and an unrepresentable one
the moment there are two.

`internal/lima.Profile` is now the only source for both sides. `renderTemplate`
substitutes from it and `verifyCompatibleConfig` compares against it, so a pin
the renderer writes but the verifier ignores — or the reverse — cannot be
expressed at all.

The zero `Profile` is refused everywhere rather than defaulted. An adapter built
on an unsupported host holds exactly that, and comparing an instance against
empty pins would accept every instance, which inverts what the pins are for.

Widening the matrix does not weaken them. The pins were never a claim about
isolation strength — both drivers are hardware virtualization, and the threat
model does not admit an adversarial agent. They answer one question: is this
instance the one Torio would have created here? That question is only meaningful
against a single expected answer, and it stays exactly as sharp when the answer
depends on the host asking it. What would weaken it is two places holding the
same literal, and that is the shape being removed.

`ProfileFor` takes the platform as arguments rather than reading the runtime, so
the whole matrix is reachable from a test on any machine. The suite proves that
the two hosts share no guest pin, that a darwin instance does not verify against
the linux profile, and that each host's rendered template carries its own digest
and not the other's. A check that only ever runs on the host it was written on
can see none of that — which the test fixtures then demonstrated by failing on
Linux, where an assertion that fed `x86_64` as the wrong architecture had been
feeding the right one.

The names of the dormant MCP guest payloads are derived from the same profile,
because a constant pair could only ever spell one architecture. Nothing in this
release packages or activates them; the failure that shape prevents is a future
release shipping the right binaries under names the CLI does not look for.

### A release carries every supported host

`v0.2.0` published `torio_0.2.0_darwin_arm64.tar.gz` and nothing else, and
`install.sh` derived exactly that name. Linux support that is real in the code
is unreachable for an operator until there is an asset to download.

A release now builds one archive per supported host into a single directory with
one `SHA256SUMS` covering both. The sums file is regenerated from the archives
present rather than appended to: appending would let a rebuilt archive keep its
old line beside the new one, and `install.sh` matches by filename, so it would
verify against whichever line came first. The lines are sorted, so the file is
identical whatever order the platforms were packaged in.

`install.sh` derives the asset from `uname -s` and `uname -m`. The platform is
not a flag — an installer that let you ask for the wrong architecture would
verify a checksum and then place a binary that cannot execute.

The platform list in `scripts/package_release.py` is asserted against the Go
profile table. A host shipped without pins installs cleanly and then refuses
every command; a host with pins and no archive cannot be installed at all.
Neither is possible without that assertion failing first.

### An unsupported host is refused before it installs anything

`internal/cli/cli.go` now resolves the host profile once, before the command
tree runs, and exits with `unsupported_host` and the precondition code (3) when
there is none.

The Lima adapter already failed closed on its own — it holds the zero profile
and every operation that needs a pin refuses. But that message arrives inside
the first command that needs one, which is after the operator has been told to
install Lima and create a VM that could never verify. An unsupported host is a
precondition of the machine, not a usage mistake, and it now reads as one.

### `torio project add` works against Hermes Agent 0.19.1

`project add` failed closed on a guest that was working perfectly, reporting
`REGISTRATION_FAILED: inspect the Hermes project exited 1`.

Hermes Agent 0.19.1 exits non-zero from `hermes project show` for a project that
does not exist. 0.19.0 exited 0 and wrote only a stderr diagnostic. Torio was
written against the older behaviour and read the non-zero exit as evidence of a
broken CLI, so adding the first project to a fresh VM could not succeed.

Neither exit code answers the question being asked, so the answer no longer
comes from one. `show` describing a project means it exists; `show` describing
nothing sends the question to `hermes project list`, whose output carries slugs
and names and never a path. A slug `list` names but `show` will not describe is
unverifiable state and stays fail-closed, as does `list` failing at all.

This is the defect the Linux gate found on the first run it was ever given, and
it would have shipped to a macOS operator on a fresh VM too.

### A real guest gates every pull request

No automated job in this repository had ever booted a Torio guest. Hosted macOS
runners are themselves virtual machines and report `kern.hv_support = 0`, so the
platform journey could only run its `host` half there — everything from `vm
start` onwards was verified by hand or not at all.

Hosted Linux runners expose `/dev/kvm`. The full journey — bootstrap, Brain,
backend, project attach and remove — now runs against a real VM on every pull
request. macOS keeps the release gate at the `host` stage, because it is the
only way to prove the darwin archive installs and runs on darwin.

That is a verification consequence before it is a cost one, and the
`project add` fix above is the first thing it caught.

### The destination egress allowlist is rejected

`AGENTS.md` §4 lists a domain network allowlist among the things Torio must not
implement. ADR-0004 proposed one anyway, as the destination-keyed half of guest
egress control, and named it as the only part of that work which addressed data
exfiltration at all.

The contradiction was recorded rather than resolved. Both documents named the
same two exits — amend the prohibition, or reject the allowlist and keep saying
that exfiltration is unsolved — and both said that until someone chose,
nothing would be built on it. That block sat in the first source of truth, where
it also stalled the uid-keyed half, because a reader could not tell how much of
"egress control" was still live.

ADR-0006 chooses. The allowlist is rejected, the prohibition stands unamended,
and no later component may narrow or scope it without a record that supersedes
this one.

The reasoning is about where this product is used, not about how strong the
mechanism would be. The box runs in the operator's own workplace, against the
operator's own Jira and Confluence. A control aimed at an adversary who has
already been given legitimate access to that content is not what this box is
for, and the threat model excluded an adversarial agent before this decision
existed — the rejection follows from that exclusion rather than adding an
exception to it.

What the record refuses to do is soften the residual. Exfiltration is unsolved,
has no owner and no plan. An agent that reads content legitimately through a
permitted tool can send it anywhere: its own shell, a Git remote, an HTTP
request, a DNS query. No mechanism in this repository partially mitigates that,
and ADR-0006 states that none may be described as doing so — custody bounds what
the agent can steal, root-owned policy bounds which tools it can call, and
neither observes what those tools return.

Two things it deliberately does not decide. The uid-keyed half of egress control
keys on the identity of the calling process rather than on a destination, was
never covered by the §4 prohibition, and remains what ADR-0004 left it: proposed
and unbuilt. And ADR-0004 §8, the configurable upstream endpoint, keeps its
stated purpose as a seam for a later decision; it was never a commitment to this
allowlist.

ADR-0004 gains a `Superseded in part by:` header pointing at ADR-0006 — the
first use of a convention this release introduces. It is a pointer. The
superseded paragraph is not rewritten, because an accepted record is not edited
to hide what it said.

Nothing about the binary changes. What changes is that a reader auditing this box
gets a direct answer to "what stops the agent sending my Confluence page
somewhere else" — nothing does — instead of a control they would have to test to
find out it was cosmetic.

## Not delivered

- **The MCP broker daemon, relay, OAuth lifecycle and upstream transport remain
  outside the release surface**, under ADR-0004. `torio mcp install` and `torio
  mcp status` provision and verify the `torio-mcp` identity, its private home,
  the client group and the root-owned policy directory, and report what those
  policy documents grant. No binary in this release carries MCP traffic
  upstream, and a reported write tool is a count, not a capability.
- **Exfiltration is unsolved, and as of ADR-0006 it has no owner and no plan.**
  The trust boundary is the edge of the VM. Torio does not stop an agent leaking
  what it has read; the destination-keyed allowlist that was the only proposal
  aimed at it is rejected rather than pending, and the uid-keyed half of egress
  control remains proposed and unbuilt.
- **arm64 Linux and Intel Macs are not supported**, and this release does not
  make them closer to being so.

## Upgrade

Download the release assets with a GitHub client that already has repository
access, then let the installer verify `SHA256SUMS`:

```bash
gh release download v0.3.0 -D /tmp/torio-rel
scripts/install.sh --version 0.3.0 --base-url file:///tmp/torio-rel
```

The installer picks the archive for the machine it is running on. Confirm the
installed build:

```bash
torio version
```

An existing macOS instance needs nothing. The darwin pins are byte-identical to
`v0.2.0` — same driver, same architecture, same image URL and digest — so `torio
vm init` stays idempotent against it and verification reports no drift.

A Linux host starts from `torio vm init`. Its instance is a different machine
from any macOS one you run: separate guest, separate Brain, separate projects.
Torio does not move state between hosts and this release does not add a way to.

`torio project shell` still forwards the host SSH agent only for the active
operator session. The persistent Hermes service receives no forwarded agent
socket, and Torio performs no automated push, merge, tag, or release.
